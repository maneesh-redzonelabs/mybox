MyBox Portal — API Specification

REST API contract for a Node.js (Express) backend and PostgreSQL "MyBox" schema, consumed by a React single-page app. Derived from the MyBox.html prototype's functional flow and MyBox-database-schema.html / MyBox-database.sql.

1. Overview & Architecture

MyBox.html is currently a client-only prototype that keeps all data in localStorage. This specification defines the REST API needed to move that same functional flow — mobile/OTP login, onboarding, Dashboard, My Family, My Policies, My Vehicles, Update Profile, Sign Out and Export — onto a real Node.js backend backed by the PostgreSQL MyBox schema described in MyBox-database-schema.html / MyBox-database.sql.

3. Authentication & OTP

Mirrors the two-step login in MyBox.html (sendOtp() / verifyOtp()). The prototype accepts a hardcoded OTP (123456); in the real API this is replaced by a generated, time-limited OTP delivered via SMS (see Implementation Notes for the storage table this requires).

  1. User enters a 10-digit mobile number → POST /auth/otp/send.
  2. User enters the 6-digit OTP → POST /auth/otp/verify.
  3. If the mobile number already has a profile, the API returns a JWT and the user record (equivalent to startSession()) and the SPA routes straight to the Dashboard.
  4. If the mobile number has no profile, the API returns exists: false and the SPA routes to the onboarding form; submitting it calls POST /profile, which creates the user and auto-seeds the "Self" family member row, then returns a JWT.
POST /auth/otp/send No auth

Generates and dispatches an OTP for the given mobile number. Equivalent to the client-side sendOtp() validation plus a real SMS dispatch.

Request body

{ "mobile": "9876543210" }

Response 200

{
  "data": {
    "mobile": "9876543210",
    "otpExpiresInSeconds": 300
  }
}

Errors

400 VALIDATION_ERROR   -- mobile is not exactly 10 digits
429 RATE_LIMITED        -- too many OTP requests for this mobile in a short window
POST /auth/otp/verify No auth

Verifies the OTP. Returns whether a profile already exists for the mobile number, and a JWT when one does — letting the SPA decide between "go to Dashboard" and "go to onboarding", exactly like verifyOtp() in MyBox.html.

Request body

{ "mobile": "9876543210", "otp": "123456" }

Response 200 — existing user

{
  "data": {
    "exists": true,
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "user": {
      "id": 1,
      "mobile": "9999999999",
      "name": "Maneesh Sharma",
      "email": "maneesh.sharma@redzonelabs.in",
      "dateOfBirth": "1985-05-10"
    }
  }
}

Response 200 — new mobile number

{ "data": { "exists": false } }

Errors

400 VALIDATION_ERROR   -- malformed mobile/OTP
401 INVALID_OTP        -- OTP incorrect or expired

4. Profile

Covers onboarding (completeOnboarding()) and the Update Profile modal (openUpdateProfile() / saveUpdateProfile()).

POST /profile No auth (uses verified-mobile token)

Creates the user profile after a brand-new mobile number passes OTP verification. The mobile number itself is taken from the OTP-verification step, never re-typed by the client. Automatically seeds exactly one "Self" family member row from this same data (name, date of birth, mobile), with livingTogether = "NA" — matching completeOnboarding().

Request body

{
  "name": "Jane Doe",
  "email": "jane@example.com",
  "dateOfBirth": "1990-02-18"
}

Response 201

{
  "data": {
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "user": {
      "id": 7,
      "mobile": "9876500000",
      "name": "Jane Doe",
      "email": "jane@example.com",
      "dateOfBirth": "1990-02-18"
    }
  }
}

Errors

400 VALIDATION_ERROR   -- name blank / email invalid / dateOfBirth malformed
409 ALREADY_EXISTS      -- a profile already exists for this mobile number
GET /profile Bearer token

Returns the signed-in user's profile. Used to populate the topbar, the Update Profile modal, and the "from profile" Mobile No. / data shown on the Self family row.

Response 200

{
  "data": {
    "id": 1,
    "mobile": "9999999999",
    "name": "Maneesh Sharma",
    "email": "maneesh.sharma@redzonelabs.in",
    "dateOfBirth": "1985-05-10"
  }
}
PUT /profile Bearer token

Updates name / email / date of birth (mobile number is immutable — it is the login identity). Equivalent to saveUpdateProfile(). Because the Self family row mirrors the profile, the API also re-syncs that row's name, date of birth and mobile in the same transaction.

Request body

{
  "name": "Maneesh Sharma",
  "email": "maneesh.sharma@redzonelabs.in",
  "dateOfBirth": "1985-05-10"
}

Response 200

{ "data": { "id": 1, "mobile": "9999999999", "name": "Maneesh Sharma",
             "email": "maneesh.sharma@redzonelabs.in", "dateOfBirth": "1985-05-10" } }

Errors

400 VALIDATION_ERROR   -- name blank / email invalid

5. My Family

MyBox.html edits the whole family list in the browser (familyDraft) and only talks to storage once, when Save is clicked, replacing the entire collection. The API mirrors that exactly with a single bulk endpoint, so the React Save/Cancel buttons map 1:1 to one network call each (Cancel never calls the API — it just re-fetches/discards local state).

GET /family-members Bearer token

Returns all family members for the signed-in user, Self row first, with age computed server-side from v_family_members (same logic as the client's calcAge()).

Response 200

{
  "data": [
    {
      "id": 11, "name": "Maneesh Sharma", "dateOfBirth": "1985-05-10", "age": 41,
      "relationship": "Self", "mobile": "9999999999", "livingTogether": "NA", "isSelf": true
    },
    {
      "id": 12, "name": "Priya Sharma", "dateOfBirth": "1988-03-15", "age": 38,
      "relationship": "Spouse", "mobile": "9876543210", "livingTogether": "Yes", "isSelf": false
    }
  ]
}
PUT /family-members Bearer token

Replaces the user's entire family member list in one transaction — matching saveFamilyMembers(), which filters out blank rows, validates, then overwrites user.familyMembers. Send every row currently in the table (new rows without an id, edited rows with their existing id); rows omitted from the payload are deleted. The client does not need to send the Self row — the server always keeps exactly one, derived from the profile, and ignores/rejects any attempt to edit or omit it (see Implementation Notes).

Request body

{
  "familyMembers": [
    { "id": 12, "name": "Priya Sharma", "dateOfBirth": "1988-03-15",
      "relationship": "Spouse", "mobile": "9876543210", "livingTogether": "Yes" },
    { "name": "Aarav Sharma", "dateOfBirth": "2014-09-20",
      "relationship": "Son", "mobile": "", "livingTogether": "Yes" }
  ]
}

Response 200

{ "data": [ /* full, reloaded list incl. Self row, same shape as GET */ ] }

Errors

400 VALIDATION_ERROR   -- missing name/relationship/livingTogether, bad mobile format
400 SELF_ROW_LOCKED    -- payload tried to edit, remove, or duplicate the Self row

9. Validation Reference

Server-side mirror of every client-side rule already enforced in MyBox.html, so the API rejects anything the UI shouldn't have allowed through in the first place.

FieldRule
mobileExactly 10 digits: ^[0-9]{10}$
email^[^\s@]+@[^\s@]+\.[^\s@]+$
family.relationshipOne of: Self, Spouse, Son, Daughter, Father, Mother, Brother, Sister, Doughter-in-law, Son-in-law, Uncle, Aunt, Cousin Sister, Cousin Brother
family.livingTogetherYes / No — forced to NA and read-only when relationship is Self
policy.policyTypeLife Insurance / Health Insurance
policy.emiFrequencyMonthly / Quaterly / Half Yearly / Yearly / Single Premium
policy.policyTermYears / payingTermYearsInteger, 1–60
vehicle.registrationNoIndian RTO format: ^[A-Z]{2}[0-9]{1,2}[A-Z]{1,3}[0-9]{4}$ (client uppercases before sending)
vehicle.vehicleTypeCar / Bike / Scooty
vehicle.modelYearInteger, 1990–(current year + 1)
vehicle.makeNon-empty string — client offers a curated dropdown of Indian automobile manufacturers, but the API stores free text (not a DB enum), so it never blocks a manufacturer missing from that list

11. Implementation Notes

OTP storage is not in MyBox-database-schema.html The prototype hardcodes MOCK_OTP = '123456' and never persists anything OTP-related. A real backend needs a small additional table, e.g.: 
CREATE TABLE otp_requests (
    id          BIGSERIAL PRIMARY KEY,
    mobile      VARCHAR(10) NOT NULL,
    otp_hash    TEXT NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    attempts    SMALLINT NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_otp_requests_mobile ON otp_requests(mobile);
This is additive to the existing schema and does not change users/family_members/policies/vehicles.
living_together CHECK constraint needs updating for "NA" MyBox.html now forces livingTogether = "NA" on the Self row, but the published family_members.living_together column in MyBox-database.sql still has CHECK (living_together IN ('Yes', 'No')). This migration is required before the bulk PUT /family-members endpoint can persist a Self row: 
ALTER TABLE family_members DROP CONSTRAINT family_members_living_together_check;
ALTER TABLE family_members ADD CONSTRAINT family_members_living_together_check
    CHECK (living_together IN ('Yes', 'No', 'NA'));
No DB-level guarantee of exactly one Self row per user The app's UI enforces "exactly one Self row, created at signup, never deletable" entirely client-side. To make the SELF_ROW_LOCKED rule in PUT /family-members safe under concurrent requests, add a partial unique index: 
CREATE UNIQUE INDEX uq_family_members_one_self_per_user
    ON family_members(user_id) WHERE relationship = 'Self';
Bulk "replace whole list" semantics. Each of PUT /family-members, PUT /policies, PUT /vehicles should run inside a single DB transaction that deletes every existing row for that user/collection not present in the payload, upserts the rows that are present, and returns the freshly reloaded list — exactly mirroring how saveFamilyMembers() / savePolicies() / saveVehicles() overwrite the in-memory array in one shot on the client.
Computed fields stay computed. age, maturityDate and nextPremiumDate are never written to the database — they depend on "today", exactly as noted in MyBox-database-schema.html. age/maturityDate come from the v_family_members/v_policies views; nextPremiumDate is computed in application code, porting the logic in calcNextPremiumDate() (roll the start date forward one EMI cycle at a time until it lands on/after today; "Single Premium" → null).
Export stays client-side. The Excel/PDF export in MyBox.html (SheetJS + jsPDF) runs entirely in the browser against data already fetched via the GET endpoints above, so no dedicated export endpoint is required. If server-side export is wanted later (e.g. to avoid shipping those libraries to the client), it would be a GET /family-members/export?format=xlsx|pdf-style addition layered on top of this spec, not a replacement for it.

Service layer example

// src/api/client.js
const BASE_URL = '/api/v1';

async function request(path, options = {}) {
  const token = localStorage.getItem('mybox_token');
  const res = await fetch(BASE_URL + path, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
  });
  const body = await res.json();
  if (!res.ok) throw body.error;   // { code, message, fields? }
  return body.data;
}

export const api = {
  sendOtp: (mobile) => request('/auth/otp/send', { method: 'POST', body: JSON.stringify({ mobile }) }),
  verifyOtp: (mobile, otp) => request('/auth/otp/verify', { method: 'POST', body: JSON.stringify({ mobile, otp }) }),
  createProfile: (payload) => request('/profile', { method: 'POST', body: JSON.stringify(payload) }),
  getProfile: () => request('/profile'),
  updateProfile: (payload) => request('/profile', { method: 'PUT', body: JSON.stringify(payload) }),
  getFamilyMembers: () => request('/family-members'),
  saveFamilyMembers: (familyMembers) => request('/family-members', { method: 'PUT', body: JSON.stringify({ familyMembers }) }),
  getPolicies: () => request('/policies'),
  savePolicies: (policies) => request('/policies', { method: 'PUT', body: JSON.stringify({ policies }) }),
  getVehicles: () => request('/vehicles'),
  saveVehicles: (vehicles) => request('/vehicles', { method: 'PUT', body: JSON.stringify({ vehicles }) }),
  getDashboardSummary: () => request('/dashboard/summary'),
};

Save button → API call (My Family example)

Directly mirrors saveFamilyMembers(): client-side validation first (same rules as §9), then one PUT with the full, cleaned row list; on success, re-render the table from the response (which now includes the server-managed Self row) and refresh the dashboard counts. 

async function handleSaveFamily(rows) {
  // 1. same client-side checks MyBox.html already does (name, relationship, livingTogether, mobile format)
  const cleaned = validateAndCleanFamilyRows(rows);

  // 2. one network call, replacing the whole collection
  const updated = await api.saveFamilyMembers(cleaned);

  // 3. re-render from the authoritative server response
  setFamilyMembers(updated);
  refreshDashboardCounts();
}
